# 예상 공정표 검증

이미지 산식은 `ceil(Σ(부위 물량 × 주 직종 품 × 할증) / 주 직종 인원)`이다. 대기는 작업일에서 빼고 달력 날짜로 이어 붙인다. 토요일은 작업, 일요일은 휴무, 공휴일은 목공만 휴무다. 이미지에 없는 준비·청소·인원·면적 환산을 더하지 않는다.

## API와 입력

1. `GET /projects/{id}/expected-plan/inputs`: 본인 프로젝트의 사용 가능 DB 품·규격·단위·조건과 `dataset_id`를 확인한다.
2. `POST /projects/{id}/expected-plan`: 사용자가 입력한 시작일·물량·주 직종 인원·대기일과 확인한 자료 버전을 보낸다.
3. `GET /projects/{id}/plan?kind=expected`: 저장본만 읽는다. 입력이 없으면 422, 남의 프로젝트는 404다. 새 버전을 만들 때 본 `seen_version`이 다르면 409다.

예시는 합성 입력이며 사용자 집의 측정값이 아니다. `dataset_id`는 첫 API 응답값, `seen_version`은 저장된 최신 공정표 버전(없으면 0)을 사용한다.

```json
{
  "start": "2026-12-01",
  "dataset_id": "조회한-자료-버전-UUID",
  "seen_version": 0,
  "trades": [
    {
      "trade": "dobae",
      "crew": 2,
      "wait_days": 0,
      "items": [
        {"record_key": "UP-S15-R00250", "quantity": "100", "unit": "m2", "part": "wall", "accept_conditions": true}
      ]
    }
  ]
}
```

공정은 프로젝트에서 고른 공정과 일치해야 한다. 보조 인원은 `crew`에 넣지 않는다. 면적·길이·개수는 사용자가 입력하며 DB의 예시 평면도를 자동 적용하지 않는다. 동일 부위·동일 행의 중복 합산은 거부한다. 값·단위·직종·조건·활성 및 계산 가능 버전이 맞지 않으면 422로 중단한다. 한 공정은 120작업일 이내이고 현재 공휴일 자료가 있는 2027년까지 계산한다.

## 임시 선택 Fixture와 프런트 인계

정식 화면은 수정하지 않았다. `backend/tests/test_reference_plan.py`의 합성 요청을 임시 입력 Fixture로 사용한다. 도배 자재 기본 1/기본 2는 임시 선택 이름이며 단가·품·기간을 부여하지 않는다.

| 선택 항목 | 확인할 DB 행 | 사용자 단위·부위 |
|---|---|---|
| 도배 | UP-S15-R00250(합판·석고보드), UP-S15-R00265(콘크리트·모르타르) | m2, wall / ceiling |
| 천장 평탄화 | UP-S16-R00013(틀), UP-S16-R00263(석고판) | 각각의 m2, ceiling |
| 외벽 단열 보강 | UP-S10-R00206(타정, 두께 50 초과~100 이하) | m2, wall |
| 문틀 교체 | UP-S13-R00263(목재 900×2100, D=115) | ea, frame |
| 문짝 교체 | UP-S13-R00134(여닫이, 36mm, 900×2100, 20kg 이하) | ea, leaf |
| 천장 몰딩 | UP-S11-R00307(50×50 미만) | m, trim |
| 걸레받이 | UP-S11-R00421(MDF, 높이 75~120) | m, trim |

같은 공정 안에서도 주 직종이 다르면 현재의 인원 하나로 합산하지 않고 422(`occupation_crew_required`)로 중단한다. 예를 들어 건축목공 몰딩과 내장공 걸레받이의 직종별 인원이 다른 일정은 추가 입력 계약이 필요하다. 같은 주 직종의 다중 항목은 지원한다. 원본 셀의 표시 정밀도로 확인한 Excel 표현 오차는 품을 읽을 때 제거하고 원시값과 사용값을 함께 보존한다.

모든 규격에 위 행을 적용할 수 있는 것은 아니다. 원본 규격과 적용 조건을 먼저 보여 주고 확인을 받아야 한다. 자재가 필요한 문틀·문짝·몰딩·걸레받이의 기본 1/기본 2 상태는 항목별로 분리하고 해제 시 지우도록 프런트 담당자가 연결한다. 기존 `door`를 문틀·문짝으로 자동 변환하지 않는다. 선택/해제 UI는 이번 API Fixture 테스트의 검증 대상이 아니다.

입력과 DB 행·조건·가산·출처·자료 버전·해시는 `plans.basis_snapshot`에 버전별로 남는다. 과거 저장본은 지우지 않는다. 기존 구형 조회·업체 일정 흐름은 유지하며 새 입력 버전은 구형 재계산으로 덮어쓰지 못한다. 새 expected 경로에 대한 검증과 구형 전체 흐름의 이관을 구분해야 한다.

## 에이전트와 RAG

`schedule(state)` → `chat.tools.read_schedule(ctx)` → `schedule.expected.agent_context` → 본인 저장본 조회 → DB 세션 닫기 → `llm.structured` → `AgentAnswer` 순서다. 다른 에이전트·공용 ChatState·LLM SDK 경계는 수정하지 않았다. 공용 추가 파일은 `chat/tools.py`다. 일정 MCP는 사용하지 않는다.

LLM은 준비된 근거 키만 선택한다. 숫자나 새 사실을 자유롭게 쓰지 않는다. 실패하면 `failed=True`이고 기존 그래프가 실패 문구를 보여 준다. 로그는 상태·경과 ms·호출 수·프롬프트 버전만 남긴다. 실제 질문 해석 품질과 자유서술 품질은 Stub 테스트로 판단할 수 없다.

`knowledge.service`와 `repository`는 비어 있어 RAG 검색은 연결하지 않았다. 검색 도구가 자료 버전·행 키·출처·페이지·검토 사유를 반환하면 `chat/tools.py`를 통해 연결한다. 자료 임베딩의 존재만으로 검색 성공·근거 일치율을 주장하지 않는다. 순위 평가는 별도의 관련 문서 정답 라벨이 필요하다.

## 성능 평가

[성능지표](성능지표.md)의 공정표 결과·LLM 답변·RAG 검색·응답 속도·비용 기준을 따른다. 이번 1차 개발이 최초 Baseline이며 이후 개발 버전과 같은 조건으로 비교한다. 기존 저장소 코드는 비교 대상이 아니다.

기존 코드 비교용 러너·보고서 생성기·합성 평가 자료는 삭제했다. 계산 엔진·API·에이전트의 기능 테스트는 유지한다. 실제 LLM 및 전체 흐름의 성능 측정 환경과 결과는 아직 없으며, 미측정 상태다. 기능 테스트 결과를 이 성능 수치로 대체하지 않는다.
