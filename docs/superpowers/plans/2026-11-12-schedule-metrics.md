# 예상 공정표와 측정 계획

- 범위: 이미지 산식, 공종별 달력, 공정표 에이전트, 재현 가능한 평가와 바탕화면 보고서. MCP와 다른 에이전트·정식 화면은 제외한다.
- 산식: 부위별 물량 × 주 직종 품 × 할증을 합산한 뒤 주 직종 인원으로 나눠 한 번 올림한다. 작업 외 대기·보호·건조 구간은 생성하지 않는다.
- 입력: 수량·품·할증·인원은 명시적으로 받는다. 예시 평면도나 보조 인력을 실제 입력으로 바꾸지 않는다.
- 기존 API 연결: 기존 가정값 사용 여부에 대한 사용자 답변을 반영한다. 저장본은 삭제하지 않고 산식 버전을 구분한다.
- 에이전트: 기존 `schedule(state)`와 `llm.structured`를 유지한다. 도구는 본인 프로젝트의 저장된 예상 공정표만 읽고 DB 세션을 닫는다. 저장·확정 기능은 제공하지 않는다.
- RAG: 현재 검색 함수가 비어 있으므로 검색 시스템은 추가하지 않고 연동 조건과 미측정 사유를 기록한다.

## 실행 순서

1. 이번 1차 개발을 최초 Baseline으로 고정한다. RAG 포함 성능지표의 정답·측정 조건을 정의한다. 기존 저장소 코드는 비교하지 않는다.
2. 산식·작업일·선후관계·입력 검증 테스트의 실패를 확인하고 최소 구현을 더한다.
3. 에이전트의 성공·누락·실패·접근 제어와 LangGraph 호출 계약을 검증한다.
4. 1차 개발에서 실제 LLM과 전체 사용자 흐름을 측정한 뒤, 이후 개발 버전과 같은 조건으로 비교한다. 미측정 항목은 수치를 만들지 않는다.
5. 관련 회귀·Ruff·저장소 검사를 실행하고, 확인한 실제 바탕화면에 배타적 생성으로 Markdown과 JSON을 저장한다.

## 검토할 경계

- 0/음수/NaN/Infinity/불리언 인원, 잘못된 공정·중복 공정, 전체 일정 상한.
- 토요일, 일요일, 공휴일과 일요일 중복, 작업 외 구간 미생성, 잘못된 확정 날짜.
- 실패를 성공률에 포함하거나 빈 출력의 스키마 통과를 응답 성공으로 취급하지 않는다.
- Stub 속도와 실제 LLM 품질·비용을 구분한다. 없는 검색 정답이나 토큰 사용량을 만들지 않는다.
- 보고서 재실행과 이름 충돌은 기존 파일을 보존해야 한다.

## 성능 평가 기준 정정

이번 개발이 1차 Baseline이다. 기존 저장소 코드 비교는 제외한다. 이후 개발은 1차 개발과 공정표 결과·LLM 답변·RAG 검색·응답 속도·비용 지표로 비교한다. 세부 정의와 미측정 항목은 `evaluation/schedule/성능지표.md`를 따른다. 프로젝트의 기존 비교용 평가 자료는 삭제하고 기능 테스트만 유지한다. 실제 LLM·전체 흐름 측정은 아직 수행하지 않았다.
# 사용자 입력 기반 예상 공정표 연결

- 사용자 승인 흐름: 사용자 입력 → LLM의 조회 조건 선택 → 읽기 도구로 DB 조회 → LLM의 근거 선택 → 코드 검증 → calc 계산 → 서비스 저장 → 화면 표시.
- LLM은 숫자나 SQL을 만들지 않고 조회 조건과 근거 ID만 선택한다. DB 세션은 LLM 호출 전에 닫는다.
- 예시 평면도·표준 작업 인원은 참고값으로 출처를 남긴다. 확인되지 않은 물량·인원은 만들지 않는다.
- 도배·선택한 목공만 계산하고 자재 선택은 기간에 반영하지 않는다. 별도 대기·보호·건조 기간을 추가하지 않는다.
- 검증 순서: 계산·근거 선택 실패 테스트 → 조회 도구·생성 API → 화면 생성/재생성 연결 → 권한·동시성·회귀 검증.
- 성능지표·커밋·푸시·운영 DB 변경은 이번 작업에 포함하지 않는다.
